# SWPro V2: архитектура, границы платформ и перенос данных

Дата: 10 августа 2026 года. Документ является рабочей спецификацией V2, а не инструкцией по изменению V1.

## 1. Цель V2

V2 создается параллельно с V1 на отдельном домене `ассистент.рус` (`xn--80akivrabic.xn--p1acf`). Рабочий сайт `swpro.ru` и его база на этом этапе не меняются.

Цель — сохранить действующие данные и бизнес-правила, но заменить разросшуюся реализацию на модульное приложение с:

- понятными границами ролей и веток;
- единым механизмом наследования контента и мини-сайта;
- независимыми платформенными клиентами;
- единым интерфейсом списков, поиска, фильтров, сортировки и пагинации;
- нормальной моделью тарифов, заказа мест, оплаты и фактического использования;
- документацией, которую можно поддерживать без редактирования PHP-файлов.

## 2. Техническое решение

### 2.1. Базовая платформа

V2 — модульный Laravel-монолит на актуальной стабильной версии Laravel, совместимой с PHP 8.4 и MariaDB 10.6. Версия фреймворка будет зафиксирована в `composer.lock` в момент создания каркаса, а не оставлена «плавающей».

Причины выбора:

- миграции, очереди, планировщик и тесты уже являются частью стандартного стека;
- политики и middleware дают понятную модель доступа по ветке;
- Eloquent/Query Builder упростят безопасные запросы и пагинацию;
- Blade-компоненты подходят для быстрой компактной админки без необходимости строить тяжелую SPA;
- Vite позволяет выпускать физически разные клиентские сборки.

V2 не переносит гигантский `admin/public/crud.php`. Каждая область получает свой маршрут, контроллер, прикладной сценарий и представление.

### 2.2. Структура кода

```text
app/
  Domain/
    Identity/
    Organization/
    Subscription/
    Content/
    MiniSite/
    Checkup/
    Conversation/
    Integration/
    Help/
  Application/
    ... use cases ...
  Infrastructure/
    Persistence/
    Messaging/
    Storage/
  Http/
    Admin/
    Client/
    Api/
resources/
  views/
  js/
    client-core/
    client-telegram/
    client-vk-ok/
    admin/
docs/
  help/
  v2/
```

Правило: HTTP-контроллер принимает запрос и вызывает один сценарий. В нем не выполняются обход дерева, клонирование контента, расчет тарифов или отправка сообщений.

### 2.3. Сервисы вместо глобальных функций

| V2-сервис | Заменяет/собирает правила V1 |
|---|---|
| `OrganizationTree` | Обход ветки лидеров, предки, прямые/ветвевые лимиты. |
| `AccessPolicy` | Скоупы супер-админа, лидера, консультанта. |
| `ClientPromotion` | Безопасное превращение клиента в консультанта/лидера с идентичностями и доступом. |
| `ContentInheritance` | Copy-on-write, сброс к вышестоящей версии, происхождение записи. |
| `MiniSiteInheritance` | Наследование/копирование профиля и шаблонов. |
| `CheckupSession` и `ScoringStrategy` | Обычные и многошкальные тесты, сохранение ответа, результат. |
| `SubscriptionLifecycle` | Тариф, заказ мест, счет, оплата, активация и фактическое использование. |
| `ConversationService` | Диалог клиента, вложения, ответы и статус обращения. |
| `PlatformAdapter` | VK, OK, Telegram и web без смешивания платформенных деталей. |

## 3. Жесткая граница платформ

### 3.1. Причина

Telegram нельзя включать в код, запросы, SDK, ссылки или импорты, которые загружаются внутри VK, OK и других российских площадок. Условие `if (isTelegram)` недостаточно: ресурс уже мог быть загружен до проверки.

### 3.2. Сборки V2

| Сборка | Разрешенные интеграции | Запрещено |
|---|---|---|
| `client-core` | Общая бизнес-логика, REST API, изображения, web-функции | Любой SDK конкретной платформы. |
| `client-telegram` | Telegram WebApp/API, Telegram deep links | VK/OK SDK, если они не нужны этой сборке. |
| `client-vk-ok` | VK Bridge, OK API, нейтральный web-код | Telegram SDK, `telegram.org`, `t.me`, Telegram OIDC/API и любые Telegram imports. |
| `client-web` | Нейтральный обычный браузерный путь | Автоматическая загрузка Telegram/VK/OK SDK. |

Проверка сборки будет обязательной в CI: артефакты `client-vk-ok` и `client-web` проверяются на строки `telegram`, `t.me`, `telegram.org` и известные Telegram API адреса. Ошибка блокирует выпуск.

### 3.3. Платформенные идентичности

У человека есть одна внутренняя сущность `Person`/`Client`, а внешние идентичности — отдельные записи `ExternalIdentity` с платформой и внешним ID. Связь нескольких платформ требует явного подтверждения; V2 не должна автоматически объединять однофамильцев.

## 4. Доменная модель V2

### 4.1. Организация и доступ

- `LeaderNode`: дерево лидеров через `parent_id`.
- `Consultant`: принадлежит одному лидеру.
- `AdminAccount`: доступ в кабинет, пароль, 2FA, статус и дата активации.
- `Client`: клиентская сущность с жизненным циклом и внешними идентичностями.
- `TeamScope`: вычисляемая область видимости пользователя в его ветке.

У клиента при повышении роль не исчезает его история: он сохраняет `Client`, получает `Consultant` или `LeaderNode` и `AdminAccount`. В UI это один прозрачный сценарий «Сделать консультантом» / «Сделать лидером».

### 4.2. Контент и наследование

Каждый наследуемый объект имеет:

- `owner_type`, `owner_id`;
- `source_id` — объект, из которого создана локальная версия;
- `visibility` (`global`, `team`, `private`);
- `inheritance_state` (`inherited`, `overridden`, `hidden`);
- журнал изменения происхождения.

Это применимо к продуктам, категориям, материалам, рассылкам, тестам, шаблонам и блокам мини-сайта. Действие «Вернуть версию вышестоящего» всегда объясняет, что именно будет восстановлено.

### 4.3. Подписки и биллинг

Три разные сущности, которые V1 частично смешивает:

1. `Plan` — опубликованный тариф с ценой и максимальными правилами.
2. `Subscription` — договор/выбор тарифа конкретного лидера.
3. `SeatOrder` — заказанное на период количество мест и режим расчета.

Поддерживаются два понятных режима:

- **Предоплата:** лидер заказывает, например, 25 мест, получает счет на 25, может подготовить неактивные учетные записи; активация доступна после подтверждения оплаты и в пределах оплаченных мест.
- **По факту:** счет считается по активным участникам за период; лимиты тарифа ограничивают максимум, но не являются количеством к оплате заранее.

У счетов и оплат должен быть неизменяемый снимок цены и условий на момент выставления. Изменение тарифа позже не переписывает старые расчеты.

### 4.4. Мини-сайт и шаблоны

- `SiteTemplate` — глобальный, лидерский или консультантский шаблон.
- `MiniSiteProfile` — личный профиль с блоками и происхождением.
- При создании нового лидера/консультанта выбирается: шаблон, копия сайта вышестоящего лидера или наследование.
- Личные имя, фото, контакты и реферальный код не копируются как чужие данные.

## 5. Единая админка и UI

### 5.1. Компоненты

V2 получает общий набор Blade-компонентов:

- `AdminShell` — боковое меню, верхняя панель и мобильная навигация;
- `DataTable` — поиск, фильтры, сортировка, серверная пагинация, пустое состояние;
- `FilterBar` — описание фильтров схемой, без ручной копии на каждой странице;
- `StatusBadge` — единые статусы;
- `DetailDrawer`/`Modal` — просмотр результата/клиента/медиа без потери списка;
- `MediaPreview` — изображение, видео, аудио, файл, стикер и безопасная загрузка;
- `FormField` и `InlineHelp` — единое оформление форм и подсказок;
- `ConfirmAction` — опасные операции и сброс наследования.

Каждый список использует серверную пагинацию. Никакая страница не загружает сразу тысячи лидеров, клиентов, результатов или сообщений.

### 5.2. Дизайн

Metronic используется только как источник разрешенных дизайн-токенов, паттернов навигации и компонентов после проверки его лицензии. V2 не будет копировать старую верстку или встраивать весь шаблон без необходимости.

Требования:

- компактные рабочие экраны;
- настоящее мобильное меню справа, а не горизонтальная полоса меню;
- таблица на телефоне превращается в компактные строки с главными данными, а не уходит за экран;
- изображения и длинные строки всегда имеют `max-width: 100%`, перенос и адаптивную компоновку;
- размер текста не зависит от ширины viewport.

## 6. Help и FAQ

### Docsify

Docsify используется для опубликованной справки по адресу `/help/`:

- Markdown в Git;
- поиск, оглавление, версия и дата проверки;
- изображения/скриншоты хранятся рядом с инструкцией;
- инструкции VK/OK/Telegram разделены по платформам;
- на VK/OK-страницах нет Telegram-зависимых скриптов.

### Админский FAQ

Редактируемые ответы внутри админки остаются доменным модулем V2:

- тема, аудитория, владелец, статус черновика/публикации;
- глобальные темы создаются супер-администратором;
- лидер создает/изменяет темы в своей ветке;
- консультант — только личные или разрешенные темы;
- Docsify показывает только опубликованный снимок, а не выполняет админский PHP-код.

## 7. Стратегия миграции

### 7.1. Изоляция

- V2 разворачивается в отдельном каталоге и отдельной базе MariaDB.
- V1 не получает изменений схемы ради V2.
- Экспорт V1 делается с контролируемого read-only пользователя БД или через согласованный backup.
- Все импорты идемпотентны: повторный запуск обновляет запись по таблице соответствий, а не создает дубликаты.

### 7.2. Таблицы соответствий

В V2 обязательно ведутся:

```text
legacy_import_runs
legacy_id_maps
legacy_import_issues
legacy_reconciliation_reports
```

Каждая перенесенная запись получает пару `(source_table, source_id, target_type, target_id)` и хеш исходной версии. Любая пропущенная или конфликтная запись попадает в отчет, а не исчезает.

### 7.3. Порядок импорта

1. Справочники и юридические документы.
2. Лидеры, связи дерева, консультанты, админ-доступы и планы.
3. Клиенты и внешние идентичности.
4. Мини-сайты, шаблоны и наследуемый контент.
5. Продукты, материалы, рассылки и тесты с полной структурой.
6. Сессии тестов, ответы, результаты, обращения, сообщения и вложения.
7. История стадий, согласия, журналы и уведомления.

После каждой группы формируется сверка: количество записей, несвязанные внешние ключи, дубли внешних идентичностей, циклы дерева, отсутствующие медиа и несовпавшие результаты тестов.

### 7.4. Переход на V2

1. Внутренний импорт в тестовую базу.
2. Ручная приемка сценариев на домене `ассистент.рус`.
3. Повторный импорт свежей копии V1.
4. Короткий read-only период V1 для финального переноса изменений.
5. Переключение ссылок/ботов только после сверки.
6. V1 сохраняется доступной только для чтения до завершения контрольного периода.

## 9. Первые запреты V2

1. Не использовать V1-базу как рабочую БД V2.
2. Не переносить `crud.php` целиком или копировать его методы.
3. Не смешивать Telegram с VK/OK/web сборками.
4. Не писать отдельные таблицы, фильтры и модальные окна для каждой страницы.
5. Не разрешать неявное объединение клиентов между платформами.
6. Не переписывать историю оплаты при изменении тарифа.
7. Не включать доступ сотрудника только потому, что запись была создана: активация всегда зависит от статуса места/подписки.

## 10. Следующий технический шаг

Создать изолированный Laravel-каркас V2 на ветке `swpro-v2`, не затрагивая V1:

1. настройка приложения и отдельной БД;
2. скелет доменных модулей;
3. единый административный layout и `DataTable`;
4. проверка разделения клиентских сборок;
5. каркас мигратора V1 -> V2 без запуска на production-данных.
